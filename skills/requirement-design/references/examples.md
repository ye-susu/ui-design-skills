# 示例（examples）

## 示例 A：首次使用，信息不完整

输入：用户仅提供 TAPD 看板链接，未提供设计资产和输出位置。

预期：

1. 打开看板并读取卡片信息。
2. 询问设计资产链接和输出位置。
3. 信息未确认前，不创建 Section、不复制历史稿，也不开始设计。

## 示例 B：首次使用，信息完整

输入：用户提供 TAPD 看板链接、设计资产链接和输出位置。

预期：

1. 整理需求看板信息。
2. 创建 Section 和需求看板。
3. 整理交互稿页面清单。
4. 查找并复制历史稿；未找到时创建占位 Frame。
5. 阅读交互稿设计备注，逐页判断无需调整、设计迭代或全新设计。
6. 保留无需调整页面；先完成所有设计迭代页面，再完成所有全新设计页面。
7. 逐页对照交互稿、设计备注和终稿，完成 Design System QA。
8. 返回 Section 链接、历史稿查找结果、页面设计方式、逐页对照结果和 Design System 说明。

## 示例 C：非首次使用

输入：本对话已确认设计资产；用户提供新的 TAPD 看板链接和输出位置 `SA APP 1`。

预期：

1. 沿用已确认的设计资产，不重复询问。
2. 仅询问本次需求仍缺少的信息。
3. 信息确认后，按步骤 1–7 完成本次需求设计。

## 示例 D：错误示例——仅修改名称或文案

输入：交互稿包含“申请记录”页面：`Pending / Processed` Tabs，以及绑定门店申请卡片。

错误行为：

复制“员工管理”页面后，仅将标题改为 `Application records`，替换几段英文文案后交付。

正确行为：

1. 根据交互稿和设计备注，将历史稿中的员工列表结构替换为申请记录结构。
2. 使用 `Pending / Processed` Tabs。
3. 卡片展示申请时间、门店名称、员工姓名和审批状态。
4. 删除或替换历史稿中与申请记录无关的 `Normal / Freeze / Risk` Tabs、员工头像列表等内容。
5. 完成后与交互稿和设计备注逐页对照，再交付。

## 示例 E：需求仅调整文案

输入：步骤 5 已确认某页面只需修改一个按钮文案，其他内容保持不变。

预期：

1. 将页面归为设计迭代。
2. 只修改设计任务中明确列出的文案。
3. 不重构页面结构，不替换其他组件，不统一历史页面样式。
4. 修改后仍完成逐页对照检查。
